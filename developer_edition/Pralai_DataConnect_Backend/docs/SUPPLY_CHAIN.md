# Supply chain: pinned images, SBOMs, vulnerability scanning

What runs in production is not only our code. It is the base OS image, the database and broker images, every Python and npm package, and the
build tooling that assembled them. This page says how each is pinned, scanned and inventoried, and how an exception is granted.

## 1. Image pinning

Every **operational** image is `name:exact-version@sha256:<digest>`:

| Where | Images |
|---|---|
| `infra/docker-compose.yml`, `infra/docker-compose.fresh.yml` | postgres, redis, zookeeper, kafka, schema-registry, prometheus, kafka-ui |
| `Dockerfile` | `python:3.11.15-slim` |
| `infra/kafka-connect.Dockerfile` | `confluentinc/cp-kafka-connect:7.6.0` (the base of every `inai-connect-*:local` worker pool) |
| frontend `Dockerfile` | `node:20.20.2-alpine` |

The tag is for people; the **digest is the pin** (a tag can be re-pushed, a digest cannot). `tests/test_image_pinning.py` fails the build on any
unpinned or `latest` image in those files, and on an operational compose that pulls from the test-backend catalogue.

`docker-compose.test-backends.yml` is deliberately out of scope: it is a catalogue of throwaway third-party systems used to exercise connectors, and
many of them only publish `latest`.

**Bumping an image** (a deliberate act, in its own commit):

```bash
docker buildx imagetools inspect <name>:<new-version>     # prints the index digest, pulls nothing
# edit the `name:version@sha256:...` everywhere it appears (compose files, Dockerfiles), run the stack, run `make test`
```

## 2. SBOMs

CycloneDX 1.6, one per artifact, uploaded by `.github/workflows/security.yml` and attached to each run:

| SBOM | Generated by |
|---|---|
| Python dependencies (resolved environment) | `make sbom` -> `sbom/backend.cdx.json` (`cyclonedx-py`) |
| Backend container image (OS packages + Python) | `anchore/sbom-action` (syft) |
| Frontend production npm dependencies | `@cyclonedx/cyclonedx-npm --omit dev` (frontend repo's `security.yml`) |

## 3. Vulnerability scanning

| What | Tool | Policy |
|---|---|---|
| Python dependencies | `pip-audit` (`make audit`) | any known vulnerability fails CI |
| Backend image | Trivy | HIGH/CRITICAL **with a fix available** fails CI; unfixed findings are reported only |
| Third-party operational images | Trivy | reported (we cannot rebuild them); drives a deliberate version bump |
| Frontend npm (production) | `npm audit --omit=dev` | moderate or above fails CI |
| Frontend npm (all) | `npm audit` | reported; see accepted exceptions |

The workflow also runs **weekly**, because a dependency that was clean at merge can get a CVE with no code change to trigger CI.

## 4. Exceptions

An accepted finding goes in `.trivyignore` (images) or this page (everything else), with **a reason, an owner and an expiry date**. An expired
entry must be re-justified or removed. Currently accepted: **none**.

The frontend's former Vite/esbuild dev-server advisories (GHSA-4w7w-66w2-5vf9, GHSA-v6wh-96g9-6wx3, GHSA-fx2h-pf6j-xcff, GHSA-67mh-4wv8-2f99) were
fixed by moving to Vite 6.4.4 (`npm audit`: 0 vulnerabilities). Vite 8 was deliberately not chosen: it replaces Rollup with Rolldown, which
`@originjs/vite-plugin-federation` was not written for.

## 5. Known limits

* The private `inaiera-gateway-auth` package is not on PyPI, so `pip-audit` reports it as **skipped**. Its advisories must be tracked in its own
  repository.
* `pip-audit` audits the *resolved environment*. A developer venv can contain orphans the product does not ship (we found an unused `PyJWT`);
  CI audits a clean install, which is the authoritative result.
