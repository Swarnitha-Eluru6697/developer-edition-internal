# Database migrations (§0.69, GAP_REPORT)

Real, versioned Alembic migrations — replaces `db.py`'s former reliance
on `SQLModel.metadata.create_all(engine)` plus a growing, unversioned
list of manual `ALTER TABLE ADD COLUMN IF NOT EXISTS` statements, one
per schema change. `create_all()` only ever creates tables that don't
exist yet — it can't safely evolve an existing production schema from
one real release to the next; there was no real migration history, no
rollback path, and no way to know what schema version a given database
was actually at.

## How this is wired up

- `migrations/env.py` gets its target schema (`target_metadata`) from
  `app.models`' own real `SQLModel.metadata` — importing that module
  registers every real table — and its target database from `app.db`'s
  own real `DATABASE_URL`. Neither is duplicated or hand-maintained
  here; both come from the app's own real, existing config.
- `migrations/versions/` holds every real, ordered migration, starting
  with `..._baseline_schema.py` — a real migration generated by
  `alembic revision --autogenerate` against a genuinely fresh database,
  capturing the full schema this platform's models actually describe
  (verified directly against the already-evolved reference database:
  every column added by every prior ad-hoc `ALTER TABLE` this session
  shipped is present and correct in the baseline).
- `app/db.py`'s own `init_db()` runs `alembic upgrade head`
  programmatically (via `AUTO_MIGRATE`, see below) instead of
  `create_all()`.

## Adding a new migration (the real, required workflow from now on)

Whenever a model in `app/models.py` changes — a new column, a new
table, a changed type — do not add a manual `ALTER TABLE` anywhere.
Instead, from `backend/`:

```bash
# 1. Make the real change in app/models.py first.
# 2. Autogenerate a real migration from the real diff:
python3 -m alembic revision --autogenerate -m "add foo column to bar"

# 3. Open the generated file in migrations/versions/ and READ it.
#    Alembic's autogenerate is a real, genuine diff tool, not a rubber
#    stamp - it can miss things it has no way to infer (a real default
#    value for a NOT NULL column being added to a populated table, a
#    real data-backfill step, a column rename that it will otherwise
#    see as "drop one column, add a different one" and lose data on
#    upgrade). Edit the generated upgrade()/downgrade() functions by
#    hand for anything like that BEFORE running it against anything
#    real.
#
#    One real, known Alembic+SQLModel quirk already worked around by
#    this project's own migrations/script.py.mako template: SQLModel's
#    own column types (sqlmodel.sql.sqltypes.AutoString, etc.) need a
#    real `import sqlmodel` that autogenerate doesn't always add on its
#    own - the template already adds it to every new migration file, so
#    this shouldn't recur, but check a generated file if you ever see a
#    real NameError: name 'sqlmodel' is not defined when applying one.

# 4. Apply it locally and confirm it actually works:
python3 -m alembic upgrade head

# 5. Confirm you can also genuinely roll it back:
python3 -m alembic downgrade -1
python3 -m alembic upgrade head
```

Commit the new file in `migrations/versions/` alongside the real model
change in the same PR - a schema change and the migration that applies
it should never ship separately.

## Deployment - AUTO_MIGRATE

- Local dev / this reference environment: `AUTO_MIGRATE` defaults to
  `true` - `init_db()` runs `alembic upgrade head` automatically on
  every real app startup. Safe and idempotent; a database already at
  `head` is a real no-op (confirmed directly - running `init_db()`
  twice in a row against the same database doesn't error or duplicate
  anything).
- A real production deployment with more than one app replica should
  set `AUTO_MIGRATE=false` and run `alembic upgrade head` as its own
  explicit, separate deployment step - a CI/CD pipeline stage, or a
  Kubernetes init container/Job - that completes BEFORE any new app
  instance starts serving traffic. Running the migration at each
  replica's own startup instead is a real, known anti-pattern: N
  replicas starting concurrently could genuinely race to apply the
  same migration simultaneously. Real, concrete Kubernetes shape:

  ```yaml
  # A real Job, run as part of the deployment pipeline before the new
  # Deployment's own rollout begins:
  apiVersion: batch/v1
  kind: Job
  metadata:
    name: inaiera-agents-migrate
  spec:
    template:
      spec:
        containers:
          - name: migrate
            image: inaiera-agents-backend:<the-new-release-tag>
            command: ["python3", "-m", "alembic", "upgrade", "head"]
            envFrom:
              - secretRef: {name: inaiera-agents-db-secret}
        restartPolicy: Never
    backoffLimit: 2
  ```

  Then set `AUTO_MIGRATE=false` on the real app Deployment itself, so
  no replica ever attempts its own migration.

## Stamping an existing, already-current database

A database whose schema already matches a migration (e.g. this
reference environment's own database, whose schema was built up via
the old `create_all()` + manual-`ALTER` approach before this fix, then
confirmed column-for-column to match the new baseline migration) can
be marked as already being at that revision - WITHOUT re-running its
`CREATE TABLE` statements, which would fail against tables that
already exist:

```bash
python3 -m alembic stamp head
```

Use this only when you've directly confirmed (not assumed) that the
real, existing schema actually matches - `alembic upgrade head`, not
`stamp`, is the right command for a database that's genuinely behind.
